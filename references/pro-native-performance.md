# Pro 在线执行提速

本轮优化复用已有原生接口和归档合同，不改软件版本准入，不增加permit或逐批审批。保持当前工程、页面、完整路径、类型和owner的正确调用条件；用合并计算和请求代替反复采集同一事实。用户暂停的工程不会因工具更新而恢复。

0102进一步采用[后台准备、UI原生执行、后台回执](pro-native-pipeline.md)，包括实际线程分工、输入冻结、异步日志、采集去重及旧桥兼容范围。下面的批次合同继续适用。

## 默认执行方式

`run`默认direct，并把连续同页、无保存、兼容的独立编辑step合成一次RPC。支持合并原生创建、几何和属性动作；每个原动作仍按原顺序取得当前目标并执行。显式inspect、页面切换、保存、检查、调层、未知kind、不同页面、不同spec元数据和组内依赖都结束当前编辑组。已完成组之外的`$ref`仍按真实回执解析；需要当前组结果的step留到下一RPC。

分组只改变传输和可合并的原生边界，不改变原step的输出索引、实际动作ID、前像或完成记录。原生部分执行、批次末尾刷新失败和超时分别记录；未完成尾部不自动重放。`run --no-merge-steps`保留逐step direct兼容方式。单step既有能力不因分组上限而拒绝。

默认不按固定动作数切分跨 step 同页批次，使用实际依赖和 8MiB 编码预算；`--max-merged-actions N` 可为交互进度设置更小组。预算只分组，不拒绝已有单 step。

连续属性动作按页面和控件完整身份合并，按钮两态标志一并传入。原生批次按目标字段采集，未变化字段跳过；一次原厂历史和末尾刷新。需要连续多次读取/修改时用 `native-engineering serve` 保持客户端，省去反复启动 PowerShell/Python及载入配置，协议见[跨机使用与批量执行](portable-online.md)。

连续且范围明确的 `page-flush` 与末尾的 `root-flush` 可共用一个保存 RPC。页保存先调用，工程保存随后调用，两者仍按各自原厂语义执行和记录。遇到组内回执依赖或不兼容步骤就保留原边界。部分执行、超时或结果不明时先核对回执和实际工程状态。

原生批次回执保留在 `*-rpc-response.json`，逐步结果按原动作 ID 展开并注明共享批次。若发生可能已写入的批次失败，同批未获验证的动作记为结果不明，先回读实际状态。用 `coalesce_native_properties: false` 做逐项对照。

同页连续的`control-native-create`可共用一次原生BeforeModify历史记录和一次末尾刷新。每个控件调用原构造、defaults、DocAdd、typed setter。批内共享页面基线和索引，只检查本件新增对象，批末统一核对完整保留范围，避免逐件重读全页。无view时回落原逐项路径。显式保存发生在创建批次完成之后；`coalesce_native_creates=false`可用于保留逐对象历史/刷新或做对照。调用方应在创建动作的`after.properties`直接给最终样式，减少后续属性动作。

调层原命令包含原厂内嵌STORE及选择状态变化。本轮保留这些调用，不将调层包装进创建scope，也不声称实现了一次历史记录的通用批量调层。当前公开control-layer仅支持单目标；底层selection数组不代表多选适配已经实现。本轮先共享单次Capture中的树，不放开目标数量。

## 计算和通信

- 画面施工以一次 direct `page-view-open` 完成内部切换及原生前后核对。实际 MDI 活动页已匹配时直接沿用。只在任务需要单独取证时执行仅查看视图的 inspect。
- ABI 配置生成按各配置的 JSON 路径建立条目索引，复用已经读入并核验的源字节。发布指纹、模块定位证据、守卫字节和输出顺序仍按原合同生成。
- 动画Capture/Verify每轮只读取一次当前森林，并建立完整对象身份索引。原有raw/owned值和所有非目标动画仍逐项比较，前后两轮Verify不变，不跨mutation缓存live对象。
- 创建批次以真实 DocAdd 回执更新索引，批末读取森林并核对新增与原有对象。
- 仅处理页面控件时，不再无条件枚举策略编辑窗口；真正涉及canonical策略时仍即时检查。
- 新Bootstrap的后台worker监听本地命名事件，仅将原生Dispatch投递回原UI线程，再于后台封装并发布回复。文件队列、请求ID和回执关联继续保留。通知不可用时保留轮询回退，兼容旧桥。
- 更新engine和Python客户端本身不会替换已加载的Bootstrap。新通知能力需在后续正常连接时热接新版Bootstrap；不得为更新技能擅自关闭Pro或恢复暂停工程。

已有桥升级时，将新版transport另存为本次runtime内的新文件（例如`bridge_client_0101.py`），物化匹配预编译引擎的 scope，再按 file-only 选择流程切换业务 DLL。不要把旧scope交给只认新版transport字节的客户端，也不覆盖尚在使用的旧transport。已有Bootstrap可以继续服务同一队列并走轮询回退；启用新事件通知才需要接入新版Bootstrap，不需要每个工程重启Pro。

## 性能记录

新版回执提供`queue_wake_source`、事件/轮询pump计数及`queue_dispatch_elapsed_ms`。客户端submission记录保留各phase的UTC时点。direct各动作记录目标读取、当前摘要/计划、准备执行核对及保存的分阶段毫秒；内层Apply另外区分prepare、目标校验、apply/verify/refresh、flush/save和cleanup总耗时。

这些数值是包络时长：`apply_verify_refresh`不能解释成单独原厂绘图CPU时间，队列调度总时长也不等于某个setter时间。应以同一工程、同一方案的最终集中验收测净收益，不能将算法模拟或隔离ping结果宣称为真实Pro整页提速倍数。

## 2026-11-16 同一 Pro 实例对照

Pro 3.5.2.12210 在同一进程、原桥和队列上，依次使用原发布引擎和本轮测试引擎。按实际打开的两份隔离副本对照，复制前源 SHA 相同，两轮打开后 604 个字段前像一致。每轮在同一页面改 20 个现有文字控件颜色，再用原厂构造新增 20 个矩形。旧版默认 8 项一组，新版依页面、依赖和消息大小分组。下表墙钟包含各次执行命令开销，独立的暂存和导出时间见记录。

| 工序 | 旧版墙钟 | 本轮墙钟 | 原生调度旧版 → 本轮 |
| --- | ---: | ---: | ---: |
| 读现有文字前像 | 2.390 秒 | 2.888 秒 | 0.367 → 0.585 秒 |
| 20 个文字改色 | 5.780 秒 | 3.421 秒 | 3.139 → 1.024 秒 |
| 原生新增 20 个矩形 | 33.282 秒 | 4.331 秒 | 30.717 → 1.919 秒 |
| 页保存和工程保存 | 3.287 秒 | 3.516 秒 | 1.040 → 1.345 秒 |

本轮两类写入均为一次 RPC，旧版各为三次。每类新批次各一次原厂历史通知及刷新。文字批次的原生属性执行为 3.813 毫秒。矩形批次共享基线采集 499.542 毫秒，原生创建累计 102.161 毫秒，末尾回读 74.022 毫秒。旧版矩形的三次原生回执均成功，最后一次因原厂返回路径大小写变化而被旧客户端误报，按成功回执另行完成原厂保存。旧版首次热接 32.177 秒，本轮原桥选引擎 9.899 秒，两项测量的操作不同。

两轮文件均回读通过。22 个其他顶层控件原始字节保留，604 个字段只变更目标页控件归档。本轮原厂检查返回 0 且检查后编译标志为 1，原厂错误及警告计数未知。原厂正常关闭重开后再次验证同一份目标归档和原生 20 个颜色及 20 个矩形，随后正常退出。范围是该页的这两类动作，未执行整页重绘、模拟或现场通信。 [分项证据和耗时](portable-online-validation.json)

计时后修订了重开后首次激活的视口核对，读取原厂编辑窗口的实际客户区来校验两项对应字段。发布引擎用通过保存和回读的工程副本定点验证了再次关闭重开、首次激活、已激活无需重开、20 项颜色与 20 项矩形的原生值、工程保存和文件回读。两次测量所用 DLL 指纹分列在记录中。 [发布引擎定点验证](portable-online-validation.json)
