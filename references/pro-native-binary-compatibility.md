# 构建身份与实际接口匹配

软件大小版本、作者 EXE 指纹、安装目录和模板来源都不作为发行准入白名单。配置使用本次明确选择的程序和路径；本次准备后替换了 EXE 或复制了另一会话配置，属于目标身份变化，应按实际文件重新准备，不能用旧进程、scope 或 claim 继续。

## 两层处理

- 热接使用 Windows 的线程 hook、COM 与目标 UI STA。准备器核实际 PE32/I386，并对当前文件生成独立机制合同；不以原冷 scanner 的作者 EXE 指纹决定能否准备。它没有由此证明任何工程业务接口。
- 业务层保留实际厂商文件 SHA 供观测；整文件差异不单独拒绝调用。现有函数代码、RVA 范围、RTTI、虚表和对象布局按调用需要核对。字段或函数不符时报告具体接口，需要补对应实际结构，不能把新的实际哈希改成历史值来伪装匹配。

业务成功与失败回执中的 `vendor_binary_identity` 包含 `whole_file_sha_admission=false`、观测数量及差异。`expected_sha256` 是参考资料值，`actual_sha256` 是本次实际值，两者不会互相替代；差异记录按当前请求和 UI 线程隔离。

可选冷接的 Addin / TYPELIB / 回调协议由本次明确配置声明。参考构建曾验证的 scanner 资料保留在参考字段；不同二进制的 `static_loader_contract_supported` 不能被标成已验证。运行中原厂实际是否加载自有 Addin，单独观察和记录。

## “指纹不同”分别意味着什么

| 对象 | 处理 |
| --- | --- |
| 厂商 EXE / MFC / common / 驱动整文件 | 记录实际值及参考差异，不作作者构建准入 |
| 本次准备时选择的目标，或本次进程 creation / HWND owner | 保持本次身份一致；准备后变更则重新读取实际状态 |
| 自有脚本、ABI 资料、transport、绑定 scope | 核包与配置是否一致，混装时重新从同一完整包绑定 |
| 当前工程前像、回执与已执行请求 | 读取当前内容和请求结果，避免覆盖新修改或重复执行 |
| 实际方法代码、虚表、对象字段与序列化结构 | 报告具体不符接口并适配；不能由版本号、整文件 SHA 或 ping 推断通过 |

## 给接收智能体的规则

先看报错发生在准备、连接、配置、当前工程，还是实际业务函数。不能把所有 SHA 不同都解释成“升级软件”。包内出现的软件版本号可能仅是历史环境或空白模板来源，不能据此指定接收方升级版本。

取消整文件准入后仍要如实区分连接、文件回读、原厂检查、保存重开和本机模拟。没有在对方实际二进制和工程上做过的项目保持未完成，不能把“允许尝试”和“全部接口已兼容”混写。

更新技能后，已经生成的旧 Bootstrap 和业务 DLL 仍含旧代码。请从本版源码重新绑定、编译到新输出文件，不覆盖已加载 DLL，也不为换工具自动恢复暂停的工程。本次变更与验证见[准入变更记录](pro-native-build-admission-validation.json)。
